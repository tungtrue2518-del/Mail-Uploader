## Core design rule (do not break this)

**Every action opens a draft for manual review — the app NEVER sends an email itself. There are ZERO exceptions.** `_compose_outlook()` only ever calls `mail.Display()`, and the Thunderbird path only ever opens a `-compose` window. There is no code path anywhere that calls `.Send()`. **Do not add one** — not a "schedule send", not a "send now", not a background flush. See Round 20 for why this rule is now absolute (a scheduled draft silently went out to the whole distribution list). If a user asks for auto-send, explain this rule and that they must click Send themselves in Outlook/Thunderbird.

(Historical: Rounds 1–19 had an opt-in "ตั้งเวลาส่งอัตโนมัติ" scheduled-send exception on the Outlook แจ้งเลิกงาน card — `DeferredDeliveryTime` + `.Send()`. It was **removed entirely in Round 20** after it caused a real incident. Any mention of scheduled/deferred send, `scheduled_sends.json`, `add_scheduled_send`, the "ระบบทำงานเบื้องหลัง" background Scheduled Task, or `--background-check` elsewhere in this doc describes code that no longer exists.)

## Round 5: read quote/PO numbers from inside the PDF, not just the filename

The auto-fill for "เลขที่ใบเสนอราคา" (step1) and "เลขที่ PR&QC" (step2) used to only regex-match the **filename**. That breaks whenever the latest file in the folder has a generic name like `EXT HDD 3.5.pdf` — the real number is printed inside the document, not in the filename.

- `extract_pdf_text(path, max_pages=2)` in `mail_app.py` — uses PyMuPDF (`import fitz`, package name `pymupdf`, already installed) to pull text off the first couple of pages. Wrapped so a missing PyMuPDF or unreadable PDF just returns `""` rather than raising — never breaks the compose flow.
- `find_number_in_file(path, pattern)` — tries the filename first (cheap, matches the already-working PO-number case where the vendor names the file `PR&QC69071882.pdf`), then falls back to searching the extracted PDF text.
- `open_step1`/`open_step2` both call this instead of doing their own filename-only regex.
- Verified against a real file on this machine: `ใบเสนอราคาขั้น 1\EXT HDD 3.5.pdf` has the line `เลขที่ใบเสนอราคา : Q26072399` in its body text — `find_number_in_file()` correctly returns `Q26072399` even though the filename has nothing matching. The existing `QUOTE_NUMBER_RE = r"(Q\d{6,})"` pattern already matches this real-world format — didn't need to change it, just needed to actually look inside the file.
- **New dependency for the exe build**: PyMuPDF (`pymupdf`/`fitz`) is installed in this dev environment but there's no PyInstaller hook file for it found under `_pyinstaller_hooks_contrib` or `PyInstaller/hooks` on this machine — it usually bundles fine via PyInstaller's default import analysis since it's mostly a compiled extension, but this hasn't been verified with an actual `--onefile` build yet. **Before shipping the next exe rebuild, do a real PyInstaller build and open a PDF-backed step1/step2 send to confirm `fitz` actually works from the frozen exe** (not just `python mail_app.py`) — if it's missing, add `--collect-all pymupdf` to the PyInstaller command.

## Round 6: auto-archive to \\vsth-fsrv\IT\fix\PR&PO after step 2 sends

After `open_step2()` (the "ขั้นตอนที่ 2 / อนุมัติ+จัดส่ง" card, which works off the `ใบเสนอราคาขั้น 3` folder) successfully opens the Thunderbird draft, `archive_pr_po_file()` in `mail_app.py` **moves** the attached PDF out of the working folder into the shared archive:

- Destination: `\\vsth-fsrv\IT\fix\PR&PO\<พ.ศ. year>\<Jan..Dec>\<PO number>.pdf` — e.g. `PR&PO\2569\Jul\PR&QC69071882.pdf`. Year is **Buddhist Era** (`today.year + 543`), month is the English 3-letter abbreviation (`MONTH_ABBR` list), confirmed explicitly with the user — not Gregorian year, not a combined "Jan-2026" folder.
- Filename is **fully replaced** with just `<po_no><original extension>` — not prefixed onto the original filename. Also confirmed explicitly.
- Auto-creates the year and month subfolders if they don't exist yet (`os.makedirs(..., exist_ok=True)`) — that's the "ถ้าเป็นเดือนใหม่ให้สร้างโฟลเดอร์ทันที" requirement.
- **Race condition guard**: there's a `time.sleep(2)` between the Thunderbird `-compose` subprocess call and the file move, because Thunderbird reads the attachment off disk itself — moving the file out from under it too fast could break the attachment. 2s comfortably covers the common case (Thunderbird already running, remote-command attach is near-instant); a cold Thunderbird start could theoretically still race this, but there's no clean way to detect "Thunderbird has finished reading the attachment" from outside the process, so 2s was chosen as a reasonable balance vs. making every step-2 send feel sluggish.
- **Failure handling is deliberately non-blocking**: `archive_pr_po_file()` never raises. If the network share is unreachable, permission denied, or the PO number couldn't be extracted at all, it returns `{"ok": False, "message": ...}` which gets appended to the already-successful "email opened" message — the user sees both "เปิดฉบับร่างใน Thunderbird แล้ว" AND "ย้ายไฟล์เข้า PR&PO ไม่สำเร็จ: ..." rather than the archiving failure masking the fact the email itself sent fine. `result["archive_ok"]` is also set on the return dict if the frontend ever wants to branch on it (not currently used in `script.js` — just surfaced via the combined status message today).
- **Verification caveat**: `\\vsth-fsrv\IT\fix` was not reachable (`os.path.isdir` → `False`, `net use` showed zero mapped sessions) when tested from this automation's Bash/PowerShell shell, even though `ping vsth-fsrv` resolved fine and the same share was clearly browsable via File Explorer earlier in this session. This looks like the automation shell not carrying the interactive user's SMB auth session, not a real problem with the path or code — but it means **this feature has not been end-to-end verified against the real network share**. Test a real step-2 send and confirm the file actually lands in `\\vsth-fsrv\IT\fix\PR&PO\<year>\<month>\` before trusting it in production.

## Round 9: real Thunderbird reply for step 2 (Advice) — thunderbird_extension/

User wanted step 2 (อนุมัติ+จัดส่ง) to open as a genuine **threaded reply** to the original Advice quotation email (the one shown in their screenshot: subject `Re: ขอจัดทำใบเสนอราคา`, body containing `เลขที่ใบเสนอราคา QC69074704`) — not just a subject that *says* "Re:" (that was Round 8, kept as the fallback). Thunderbird's `-compose` CLI has zero support for this, so this required a real Thunderbird MailExtension using the Compose API (`messenger.compose.beginReply`) bridged to the Python app via native messaging. User explicitly chose this over the lighter "drive the Thunderbird UI with computer-use every send" option, trading longer build time for not needing screen control per-send.

### Architecture
- **`thunderbird_extension/manifest.json` + `background.js`** — a MailExtension (id `reply-bridge@vel-suede.local`). On load, `background.js` calls `browser.runtime.connectNative("com.velsuede.mail_uploader_reply_bridge")` and keeps that port open for Thunderbird's lifetime (auto-reconnects every 5s if dropped). Jobs arrive over the port; for each one it: `messenger.messages.query({body: searchText})` to find the original email, sorts by date and takes the newest match, `messenger.compose.beginReply(messageId, "replyToSender", {body, cc, isPlainText:true})`, re-applies those details via `setComposeDetails` (belt-and-suspenders in case `beginReply`'s override isn't honored on this TB version), then `messenger.compose.addAttachment(tabId, {file})` where `file` is reconstructed client-side from base64 (avoids needing `file://` host-permission grants entirely — the native host reads the PDF and sends bytes, not a path).
- **Native messaging host = `mail_app.py --reply-bridge-host`** (`run_reply_bridge_host()`). Thunderbird spawns this itself (via `run_reply_bridge_host.bat`, generated by `register_reply_bridge()`) the moment `background.js` connects — it's not something `mail_app.py`'s normal GUI process starts. It watches `reply_jobs/*.json` (excluding `*.result.json`) every second, forwards new ones over stdout using the standard native-messaging length-prefixed-JSON framing (`struct.pack("<I", len)` + utf-8 JSON), and any message that arrives on stdin (the extension's reply) gets written to `reply_jobs/<jobId>.result.json`.
- **`try_reply_bridge(search_text, cc, body, attachment_path, timeout_seconds=15)`** in `mail_app.py` — what `open_step2()` calls. Writes the job file, polls for the result file up to the timeout, cleans up either way, and **returns `None` (never raises) on any failure** — not registered, host not running, extension not installed, nobody answered in time. `open_step2()` treats `None` as "fall back to the normal `_compose_thunderbird` flow" and appends a note to the status message explaining the fallback happened, rather than silently pretending the reply attempt never occurred.
- **Search text**: the original email's body has the bare `QC69074704` (no `PR&` prefix), but `po_no` extracted from the working-folder PDF is `PR&QC69074704`. `open_step2()` strips `"PR&"` before searching — verified this distinction directly from the user's screenshot, don't revert it back to searching for the `PR&`-prefixed form or the query will find nothing.
- **Settings toggle** ("Reply จริงสำหรับขั้นตอนที่ 2") only registers/unregisters the **native messaging host** side (`register_reply_bridge()`/`unregister_reply_bridge()`, writes `run_reply_bridge_host.bat` + `reply_bridge_host_manifest.json` + an `HKCU\SOFTWARE\Mozilla\Thunderbird\NativeMessagingHosts\...` registry key). ## Round 22: pending-Outlook-send tracker (nags until the draft is actually sent)

**Real incident that prompted this**: on 2026-08-21, two "แจ้งเรื่องการ Standby" emails (originally opened as drafts on 2026-08-05 and 2026-08-14) went out to the ~120-person distribution list within 3 milliseconds of each other. Root-caused via Outlook COM inspection (CreationTime/SentOn/`Sent` property) + Windows Event Log (`Get-WinEvent` power-state events): the user's habit is to click "เปิดใน Outlook" then immediately shut down the PC — but `_compose_outlook()` only ever calls `mail.Display()`, never `.Send()` (confirmed: Round 20 already removed every auto-send path). If the user doesn't click Send in Outlook itself before "shutting down," and — this was the real surprise — **the PC wasn't actually shutting down, it was going to Sleep** (`Get-WinEvent` showed a Sleep→Wake pair, not a reboot; `LastBootUpTime` was unchanged), the unsent compose window survives indefinitely across sleep cycles, since Outlook itself never closes on Sleep. Stale windows accumulated across multiple days until something (most likely a stray click or `Ctrl+Enter` while alt-tabbing through old windows) finally sent them, weeks late, with stale date content.

**Fix**: a persistent, file-backed tracker that follows every Outlook draft from "opened" to "confirmed sent," and nags (in-app banner + repeating tray notification) for as long as it isn't.

- `add_pending_outlook_send(subject, category)` — called from `_compose_outlook()` right after a successful `mail.Display()`. Appends `{id, subject, category, opened_at, notified_at}` to `pending_outlook_sends.json` (gitignored, like the other runtime-state files).
- `_outlook_sent_items_has_subject(subject)` — a **fresh** `win32com.client.Dispatch("Outlook.Application")` per call, scans the most recent 100 Sent Items for an exact Subject match. Deliberately does NOT hold a live COM object reference across time/threads — Outlook COM is apartment-threaded, and the background watcher thread is a different OS thread than whichever thread pywebview dispatches JS→Python calls on; sharing a `mail` object between them without careful marshaling is a real crash risk. A fresh Dispatch() per check sidesteps that entirely (same pattern `get_outlook_contacts()` already used successfully). Subject text already encodes the full date, so an exact match is unambiguous without needing to reconcile COM's timezone-aware `SentOn` against our naive local timestamps.
- `resolve_pending_outlook_sends()` — drops entries found in Sent Items, returns the rest; **short-circuits without touching Outlook at all if the list is already empty** (so it doesn't wake/query Outlook needlessly on every poll); **on a COM exception (Outlook still starting up, etc.) returns the list unchanged rather than dropping anything** — false negatives (staying pending a bit longer than necessary) are safe, false positives (declaring something sent when it wasn't checked) are not.
- **New background thread** `watch_pending_sends` in `run_tray_and_watcher` (alongside Round 19's `watch_step3`), polling every 30s. **Must call `pythoncom.CoInitialize()` at thread start** — this is the first background-thread-initiated Outlook COM access in the codebase; without it the first COM call on a non-CoInitialize'd thread would raise. Fires a tray notification (`PENDING_SEND_NOTIFY_AFTER_MINUTES = 5` after opening, then re-notifies every `PENDING_SEND_RENOTIFY_EVERY_MINUTES = 10` for as long as it stays unsent) rather than a single easy-to-miss ping — the whole point is to interrupt the "close the lid and walk away" moment before it happens again.
- **UI**: `Api.get_pending_outlook_sends()` → `resolve_pending_outlook_sends()`. New `#pending-sends-banner` in `index.html`, right under the transient `#status-banner` — deliberately a *different, non-auto-hiding* element (orange, pulsing glow, `display:none`/`block` toggled by JS, never the `.show`-then-fade-after-6s pattern `showStatus()` uses) since this must stay visible until actually resolved, not fade after a few seconds. `refreshPendingOutlookSends()` in `script.js` polls every 10s app-wide (not just on the แจ้งเลิกงาน page — the risk is "user navigates away or closes the app," so it needs to be visible regardless of which page is open) and also fires immediately after `sendOutlookLeave()`/`sendCustom()` succeed, not just on the next poll tick.

**Verified for real, not mocked**: seeded a throwaway pending-send entry with a subject that will never exist in Sent Items — confirmed `resolve_pending_outlook_sends()` correctly leaves it pending against the **real, live Outlook Sent Items folder** (not a mock COM object). Separately confirmed `_outlook_sent_items_has_subject()` correctly returns `True` for the real subject line from the 2026-08-05 incident email (a message we independently know was actually sent) — proving the matching logic works against real data in both directions. Backend add/resolve/persist/COM-failure-safety logic also covered by a full mocked test suite (6 assertions, all passing) before the live checks. **Not yet verified**: the actual in-app banner rendering and tray notification firing — computer-use was unavailable this round to drive the GUI, so only the backend (which carries all the actual risk — the UI is a thin, declarative render mirroring the already-proven `loadStep3RenameLog()`/`loadFgStockStatus()` pattern) got hands-on verification. ## Round 23: OutlookSendGuard — HARD block on sending a stale (date-crossed) draft, not just a notification

Round 22's pending-send tracker only nags (banner + tray notification). User explicitly asked for a system that makes the 2026-08-21 incident **impossible to repeat**, not just easier to notice. This round adds an actual send-time interceptor: **`OutlookSendGuard`**, a `win32com.client.DispatchWithEvents("Outlook.Application", OutlookSendGuard)` event sink on Outlook's `ItemSend` event, registered from a new persistent thread `run_outlook_send_guard()` in `run_tray_and_watcher` (alongside Round 19's `watch_step3` and Round 22's `watch_pending_sends`).

**Logic (`OutlookSendGuard.OnItemSend`)**: for every item Outlook is about to send (from ANY source — UI Send click, automation, anything), look up its exact Subject in `pending_outlook_sends.json`. No match → return immediately, never interfere (ordinary personal/business mail through this Outlook profile is completely unaffected — this only ever touches items this app itself opened). Match found → compare `opened_at`'s calendar date against `datetime.date.today()`. Opened today → let it send normally. **Opened on an earlier day → set `Cancel[0] = True`, clear `Item.To`/`CC`/`BCC` and `Item.Save()`, then show a native `win32api.MessageBox` explaining why and telling the user to Discard and reopen from the app.**

**Critical thing learned from live testing — do not remove the recipient-clearing step:** `Cancel[0] = True` alone is **not reliably permanent**. Live-tested 2026-08-21: a stale test item was cancelled (confirmed not in Sent Items immediately after), but ~10 minutes later it appeared in Sent Items anyway, with the exact same `SentOn` timestamp as an unrelated second test send — strongly suggesting Outlook silently re-queued and re-flushed the "cancelled" item on a later Send/Receive cycle rather than treating Cancel as final disposal. **The recipient-clearing (`Item.To = ""` etc., then `Save()`) is therefore the actual guarantee, not `Cancel[0] = True`** — even if Outlook resurrects and resends the exact same item later, there is nobody left to deliver it to. Cancel is kept too (it's still the "correct"/documented API and does stop the *immediate* send attempt), but treat it as best-effort, not authoritative.

**Registration mechanics (real gotchas, not obvious from docs):**
- `DispatchWithEvents` requires a **live Windows message pump on the same thread** that created the dispatch object to ever receive the callback — `pythoncom.PumpWaitingMessages()` in a loop (not `pythoncom.PumpMessages()`, which blocks forever with no way to check `quitting["flag"]` for clean shutdown).
- This is the first background-thread-initiated Outlook COM/event access in the codebase — **must call `pythoncom.CoInitialize()`** at the top of the thread function (COM is apartment-threaded; a thread that never CoInitialize's will fail on first COM access). `watch_pending_sends` (Round 22) already established this pattern for plain COM calls; this round needed it for event sinks too.
- Must **keep a reference to the `outlook` object returned by `DispatchWithEvents` for the thread's entire lifetime** — if it gets garbage-collected, the event sink silently stops firing with no error.

**Testing methodology gotchas (burned real time on these, don't repeat):**
- Any test that calls `mail.Send()` via COM (as opposed to a human clicking Send in the Outlook UI) triggers **Outlook's own "Object Model Guard"** security prompt ("A program is trying to send an email message on your behalf") — this is unrelated to our code, happens for ANY programmatic Send(), and blocks until a human clicks Allow/Deny. This has NO effect on real usage (humans clicking Send in the UI never see this guard — it's specifically for automation) but makes live-testing via a script require a human in the loop every time.
- **Do not run the test trigger script under a short `timeout N`** — if the human hasn't clicked Allow/Deny yet when the shell timeout kills the Python process, the dialog is left orphaned and (as observed) the eventual click goes through with NO event hook alive to catch it, since the process that registered the hook is already dead. Burned one real test-email send this way (`[TEST-STALE]`, landed in the user's own inbox harmlessly, cleaned up via COM `.Delete()` afterward). Fix used: run the hook-registering harness via `run_in_background: true` with a long window (10 min), confirm via reading its output log that `"guard hook registered"` actually printed, **then** trigger the test send from a separate short-lived script.
- Test mail was always addressed `To: isdpt5@vsth.lan` (the user's own mailbox) specifically so a test failure could never reach anyone else — confirmed with the user before every Allow click.

**Verified so far**: `Cancel=True` + the MessageBox both fire correctly and on time for a stale item (user confirmed seeing the exact expected warning text, including the correctly-formatted stale date). Confirmed the same-day case is a separate untested path (not yet re-verified after adding the recipient-clear step — the "should be ALLOWED" test send DID successfully reach Sent Items in the pre-recipient-clearing version, so that path was working, but should be spot-checked again after this change since the same `OnItemSend` function is now doing more work per stale event, though the today-path is untouched code). **NOT yet verified**: whether the recipient-clearing safety net actually prevents the delayed-resend phenomenon from delivering to anyone — this was the very next test in progress when this round's context was compacted. **Next step when resuming**: re-run the same stale-item live test (harness pattern above), confirm `Item.To` is empty immediately after the MessageBox, then wait ~15 minutes and re-check Sent Items / Inbox to confirm nothing was ever actually delivered.

## Technical gotchas (don't relearn these the hard way)

- **Thunderbird `-compose` values are NOT URL-decoded.** Only escape `\` → `\\` and `'` → `\'`. Don't percent-encode — Thunderbird shows `%40` literally instead of `@`. Attachment paths use `attachment='file:///C:/...'` (forward slashes, `file://` prefix).
- **Outlook via win32com**: `outlook.CreateItem(0)` → set `.To/.CC/.Subject/.Body` → `.Display()` for a draft, or set `.DeferredDeliveryTime` (Python `datetime`) then `.Send()` to queue a scheduled send.
- **Icon system**: icons are CSS `mask-image` (`.icon` base class + `.icon-<name>` modifier pointing at `icons/<name>.svg`), colored via `currentColor`/`color`, NOT inline `<svg>` (except the hand-crafted paper-plane logo in `.brand-mark`, which is literal inline SVG). To add a new icon: download an SVG from Flaticon (Regular Rounded style, matches the rest) via the user's account, drop it in `ui/icons/`, add one `.icon-<name>` rule in `style.css`.
- **`.field-input-wrap` CSS ordering matters**: the `padding-left: 34px` override rule must appear *after* the general `.field input[type="text"] { padding: 10px 12px; }` rule in `style.css`, or the shorthand `padding` wins on the specificity tie and the icon overlaps the text.
- **Computer-use `open_application("Python 3.14 (64-bit)")` is unreliable** — it often opens "Python 3.14 Module Docs" (pydoc) instead of bringing the running app window forward. Always screenshot and close stray pydoc windows before assuming the app isn't rendering.
- If the app window renders blank/white after being minimized and force-restored (e.g. via raw WinAPI `ShowWindow`), don't fight it — `taskkill` the process and relaunch `python mail_app.py` fresh.
